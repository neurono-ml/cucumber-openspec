cucumber-openspec

cucumber-openspec converts OpenSpec spec.md files into deterministic Cucumber / Gherkin .feature files.

It uses zero-AI, deterministic TypeScript scripts — a state-machine parser + generator — to produce correct .feature files in any of the 80 Gherkin languages. No runtime dependencies beyond Node.js.

Quick Start

# Install the skill for your AI agent
npx skills add neurono-ml/cucumber-openspec

# Convert a project's specs to Gherkin
npx tsx scripts/index.ts -i ./openspec -o ./features

Features

  • Deterministic parser — state machine, 0 dependencies
  • 80 Gherkin languages — English, Portuguese, Chinese, Arabic, Japanese, and 76 more
  • Tags — @smoke, @regression, @critical at Feature, Rule, and Scenario level
  • Background — shared steps via ## Background section
  • Scenario Outline + Examples — data-driven parameterized scenarios
  • DataTables — pipe tables as step arguments
  • Doc Strings — sub-bullets converted to """ blocks
  • Delta specs — ADDED / MODIFIED / REMOVED sections for change management
  • Gherkin grammar validation — all output validated via @cucumber/gherkin
  • Localization — keywords in 80 languages via official Gherkin translations
  • Agent Skill — installable via skills.sh, works with Claude Code, Cursor, OpenCode, Codex

How It Works

OpenSpec spec.md                     →   Gherkin .feature
─────────────────────                    ─────────────────
# [@tag] Domain                           [@tag]
## Purpose                                Feature: Domain
## Background                                Background:
- **GIVEN** step                             Given step
### [@tag] Requirement: Name                  [@tag]
#### [@tag] Scenario: Name                    Rule: Name
- **GIVEN** text                                [@tag]
  | col | col |                                Scenario: Name
- **WHEN** text                                  Given text
- **THEN** text                                    | col | col |
                                                   When text
                                                   Then text

Convert an entire OpenSpec directory

Tags

cucumber-openspec supports Gherkin tags at three levels: Feature (via H1), Requirement (via H3 Rule), and Scenario (via H4).

Tags are space-separated, prefixed with @, and support hyphens: @smoke, @regression, @integration-test.

Feature-Level Tags

Add tags before the domain name in the H1 heading:

# @smoke @regression Auth Specification

Generates:

@smoke @regression
Feature: Auth

Requirement-Level Tags

Add tags before Requirement: in the H3 heading:

### @critical @slow Requirement: Login

Generates:

  @critical @slow
  Rule: Login

Scenario-Level Tags

Add tags before Scenario: in the H4 heading:

#### @smoke @regression Scenario: Successful Login

Generates:

    @smoke @regression
    Scenario: Successful Login

Complete Example

# @smoke Auth Specification
## Purpose
Authentication system.

### @critical Requirement: Login
Body text.

#### @smoke Scenario: Valid Credentials
- **GIVEN** a registered user
- **WHEN** they submit valid credentials
- **THEN** they receive a token

Generated .feature:

@smoke
Feature: Auth

  Authentication system.

  @critical
  Rule: Login
    Body text.

    @smoke
    Scenario: Valid Credentials
      Given a registered user
      When they submit valid credentials
      Then they receive a token

Background

A Background section lets you define shared steps that run before every scenario in the feature.

Syntax

Use ## Background before any ### Requirement: headings, with standard step syntax:

# Auth Specification
## Purpose
Authentication and authorization.

## Background
- **GIVEN** user is logged in
- **AND** has admin role
- **AND** API key is valid

### Requirement: Access Control
#### Scenario: Admin Dashboard
- **WHEN** user accesses dashboard
- **THEN** they see admin panel

Generates:

Feature: Auth

  Authentication and authorization.

  Background:
    Given user is logged in
    And has admin role
    And API key is valid

  Rule: Access Control

    Scenario: Admin Dashboard
      When user accesses dashboard
      Then they see admin panel

Rules

  • Background must be placed after ## Purpose and before any ### Requirement: or scenario heading
  • Steps without bold markers work: - Given user is logged in (case-insensitive keyword matching)
  • Background is rendered once per feature, before all Rules/Scenarios
  • Empty background sections produce no output

Scenario Outline & Examples

Scenario Outlines allow you to run the same scenario with different data sets using placeholders and an examples table.

Syntax

Use #### Scenario Outline: instead of #### Scenario:, then document parameterized variables with <angle_brackets> in step text. Add ##### Examples: with a pipe table providing the data.

### Requirement: Login
#### Scenario Outline: Login with different roles
- **GIVEN** user <role>
- **WHEN** they log in
- **THEN** they see <dashboard>

##### Examples:
| role    | dashboard      |
| admin   | Admin Panel    |
| viewer  | Overview       |
| editor  | Content Editor |

Generates:

  Rule: Login

    Scenario Outline: Login with different roles
      Given user <role>
      When they log in
      Then they see <dashboard>

      Examples:
        | role   | dashboard      |
        | admin  | Admin Panel    |
        | viewer | Overview       |
        | editor | Content Editor |

Auto-Detection

If you use ##### Examples: under a regular #### Scenario:, it is automatically promoted to a Scenario Outline:

#### Scenario: Login (auto-outline)
- **GIVEN** user <role>
- **WHEN** login
- **THEN** <status>

##### Examples:
| role  | status  |
| admin | success |
| guest | denied  |

Markdown Table Separators

Markdown-style separator rows (|---|---|) in examples tables are automatically skipped.

DataTables

DataTables in Gherkin provide structured data as step arguments. In OpenSpec, pipe tables indented under a step are rendered as DataTables.

Syntax

- **GIVEN** the following users exist:
  | name  | role   | email            |
  | Alice | admin  | alice@example.com |
  | Bob   | viewer | bob@example.com   |
- **WHEN** admin checks permissions
- **THEN** the user list is correct

Generates:

    Given the following users exist:
      | name  | role   | email            |
      | Alice | admin  | alice@example.com |
      | Bob   | viewer | bob@example.com   |
    When admin checks permissions
    Then the user list is correct

Rules

  • Pipe tables must be indented under the step they belong to
  • The first pipe row becomes the DataTable header
  • Subsequent rows become data rows
  • A step can have either sub-bullets (Doc String) or a pipe table (DataTable), not both
  • DataTables work in any Gherkin language — table content is language-independent

Comparison: Doc Strings vs DataTables

FeatureDoc StringDataTable
SyntaxIndented - item linesIndented `
Gherkin output""" ... """`
Best forFree-form text, expected outputStructured key-value data, multiple rows

Doc Strings

Doc Strings allow you to include larger blocks of text (expected output, JSON, XML, etc.) as step arguments.

Syntax

In OpenSpec, indented sub-bullets under a step are converted to Gherkin Doc Strings:

- **THEN** the system returns:
  - status: success
  - token: abc123
  - expires: 3600s

Generates:

    Then the system returns:
      """
      - status: success
      - token: abc123
      - expires: 3600s
      """

Real-World Example

### Requirement: API Response
#### Scenario: Successful Login
- **GIVEN** valid credentials
- **WHEN** the login endpoint is called
- **THEN** the response contains:
  - A JWT token
  - User profile with name and email
  - Session expiration timestamp
- **AND** the status code is 200

Generates:

  Rule: API Response

    Scenario: Successful Login
      Given valid credentials
      When the login endpoint is called
      Then the response contains:
        """
        - A JWT token
        - User profile with name and email
        - Session expiration timestamp
        """
      And the status code is 200

Delta Specs

Delta specs track changes to requirements over time. OpenSpec supports three delta section types: ADDED, MODIFIED, and REMOVED.

Delta Sections

Within a change spec under openspec/changes/<change-name>/specs/, use H2 headings to mark requirement groups:

# Auth Specification
## Purpose
Updated auth requirements.

## ADDED Requirements
### Requirement: Biometric Login
#### Scenario: Authenticate with Fingerprint
- **GIVEN** a registered fingerprint
- **WHEN** the user scans their fingerprint
- **THEN** access is granted

## MODIFIED Requirements
### Requirement: Token Refresh (Previously: 1 hour expiry)
#### Scenario: Refresh Token Flow
- **GIVEN** a valid token
- **WHEN** token is about to expire
- **THEN** a new token is returned

## REMOVED Requirements
### Requirement: Legacy Token Support
Feature removed — all tokens now use JWT format.

Generates:

Feature: Auth

  Updated auth requirements.

  Rule: Biometric Login

    Scenario: Authenticate with Fingerprint
      # ADDED
      Given a registered fingerprint
      When the user scans their fingerprint
      Then access is granted

  Rule: Token Refresh

    # MODIFIED: 1 hour expiry
    Scenario: Refresh Token Flow
      Given a valid token
      When token is about to expire
      Then a new token is returned

  Rule: Legacy Token Support
    Feature removed — all tokens now use JWT format.
    # REMOVED: Legacy Token Support — Feature removed ...

Localization

cucumber-openspec supports all 80 Gherkin languages. Keywords for Feature, Rule, Scenario, Given, When, Then, And, But, Background, Scenario Outline, and Examples are automatically translated using official Gherkin language data.

Usage

# Portuguese
npx tsx scripts/index.ts -i ./openspec -o ./features -l pt

# Japanese
npx tsx scripts/index.ts -i ./openspec -o ./features -l ja

# Arabic (RTL)
npx tsx scripts/index.ts -i ./openspec -o ./features -l ar

Language Header

For non-English output, the # language: header is automatically added:

# language: pt
Funcionalidade: Autenticação

  Contexto:
    Dado que o usuário está logado

  Regra: Login
    Esquema do Cenário: Login com diferentes perfis
      Dado usuário <perfil>
      Quando fizer login
      Então <resultado>

    Exemplos:
      | perfil | resultado |
      | admin  | sucesso   |
      | guest  | negado    |
