cucumber-openspec

cucumber-openspec converte arquivos OpenSpec spec.md em arquivos .feature Cucumber / Gherkin determinísticos.

Ele usa scripts TypeScript determinísticos sem IA — um parser de máquina de estados + gerador — para produzir arquivos .feature corretos em qualquer um dos 80 idiomas Gherkin. Nenhuma dependência em tempo de execução além do Node.js.

Início Rápido

# Instale a skill para seu agente de IA
npx skills add neurono-ml/cucumber-openspec

# Converta as especificações de um projeto para Gherkin
npx tsx scripts/index.ts -i ./openspec -o ./features

Funcionalidades

  • Parser determinístico — máquina de estados, 0 dependências
  • 80 idiomas Gherkin — português, inglês, chinês, árabe, japonês e mais 76
  • Tags — @smoke, @regression, @critical nos níveis Funcionalidade, Regra e Cenário
  • Background — etapas compartilhadas via seção ## Background
  • Scenario Outline + Examples — cenários parametrizados orientados a dados
  • DataTables — tabelas pipe como argumentos de etapas
  • Doc Strings — sub-itens convertidos em blocos """
  • Delta specs — seções ADICIONADO / MODIFICADO / REMOVIDO para gestão de mudanças
  • Validação gramatical Gherkin — toda saída validada via @cucumber/gherkin
  • Localização — palavras-chave em 80 idiomas via traduções oficiais do Gherkin
  • Skill para Agente — instalável via skills.sh, compatível com Claude Code, Cursor, OpenCode, Codex

Como Funciona

OpenSpec spec.md                     →   Gherkin .feature
─────────────────────                    ─────────────────
# [@tag] Domínio                        [@tag]
## Propósito                            Funcionalidade: Domínio
## Background                              Background:
- **DADO** etapa                           Dado etapa
### [@tag] Requisito: Nome                  [@tag]
#### [@tag] Cenário: Nome                  Regra: Nome
- **DADO** texto                              [@tag]
  | col | col |                              Cenário: Nome
- **QUANDO** texto                            Dado texto
- **ENTÃO** texto                              | col | col |
                                                Quando texto
                                                Então texto

Como Skill para Agente (recomendado)

Instale via skills.sh para qualquer agente compatível com SKILL.md:

npx skills add neurono-ml/cucumber-openspec

Funciona com:

git clone https://github.com/neurono-ml/cucumber-openspec.git ~/.agents/skills/cucumber-openspec

Usando npm / npx (uso direto)

Nenhuma instalação global é necessária. O projeto usa npx tsx para executar TypeScript diretamente:

# Clone o repositório
git clone https://github.com/neurono-ml/cucumber-openspec.git
cd cucumber-openspec

# Instale as dependências
npm ci

# Use
npx tsx scripts/index.ts -i ./openspec -o ./features

Exemplos

Converter um único arquivo de especificação

npx tsx scripts/index.ts -i openspec/specs/auth/spec.md -o features

Gera features/auth.feature.

Converter um diretório OpenSpec inteiro

npx tsx scripts/index.ts -i ./openspec -o ./features

Percorre openspec/specs/<dominio>/spec.md e todos os arquivos openspec/changes/<mudanca>/specs/<dominio>/spec.md.

Converter para um idioma diferente

# Português
npx tsx scripts/index.ts -i ./openspec -o ./features -l pt

# Chinês Simplificado
npx tsx scripts/index.ts -i ./openspec -o ./features -l zh-CN

# Árabe (direita para esquerda)
npx tsx scripts/index.ts -i ./openspec -o ./features -l ar

Converter uma delta change

npx tsx scripts/index.ts -i openspec/changes/add-auth/specs/auth/spec.md -o features

Isso gera features/add-auth_auth.feature com anotações de ADICIONADO/MODIFICADO/REMOVIDO.

Tags

O cucumber-openspec suporta tags Gherkin em três níveis: Funcionalidade (via H1), Requisito (via H3 Regra) e Cenário (via H4).

Tags são separadas por espaço, prefixadas com @ e aceitam hífens: @smoke, @regression, @integration-test.

Tags em Nível de Funcionalidade

Adicione tags antes do nome do domínio no cabeçalho H1:

# @smoke @regression Especificação de Autenticação

Gera:

@smoke @regression
Funcionalidade: Autenticação

Tags em Nível de Requisito

Adicione tags antes de Requisito: no cabeçalho H3:

### @critical @lento Requisito: Login

Gera:

  @critical @lento
  Regra: Login

Tags em Nível de Cenário

Adicione tags antes de Cenário: no cabeçalho H4:

#### @smoke @regression Cenário: Login Bem-sucedido

Gera:

    @smoke @regression
    Cenário: Login Bem-sucedido

Exemplo Completo

# @smoke Especificação de Autenticação
## Propósito
Sistema de autenticação.

### @critical Requisito: Login
Texto do corpo.

#### @smoke Cenário: Credenciais Válidas
- **DADO** um usuário registrado
- **QUANDO** ele enviar credenciais válidas
- **ENTÃO** ele recebe um token

Arquivo .feature gerado:

@smoke
Funcionalidade: Autenticação

  Sistema de autenticação.

  @critical
  Regra: Login
    Texto do corpo.

    @smoke
    Cenário: Credenciais Válidas
      Dado um usuário registrado
      Quando ele enviar credenciais válidas
      Então ele recebe um token

Background

Uma seção Background permite definir etapas compartilhadas que são executadas antes de cada cenário na funcionalidade.

Sintaxe

Use ## Background antes de qualquer cabeçalho ### Requisito:, com a sintaxe padrão de etapas:

# Especificação de Autenticação
## Propósito
Autenticação e autorização.

## Background
- **DADO** usuário está logado
- **E** tem perfil de administrador
- **E** a chave de API é válida

### Requisito: Controle de Acesso
#### Cenário: Painel do Administrador
- **QUANDO** usuário acessa o painel
- **ENTÃO** ele vê o painel administrativo

Gera:

# language: pt
Funcionalidade: Autenticação

  Autenticação e autorização.

  Contexto:
    Dado usuário está logado
    E tem perfil de administrador
    E a chave de API é válida

  Regra: Controle de Acesso

    Cenário: Painel do Administrador
      Quando usuário acessa o painel
      Então ele vê o painel administrativo

Regras

  • O Background deve ser colocado após ## Propósito e antes de qualquer cabeçalho ### Requisito: ou de cenário
  • Etapas sem marcadores em negrito também funcionam: - Dado usuário está logado (correspondência de palavra-chave insensível a maiúsculas/minúsculas)
  • O Background é renderizado uma vez por funcionalidade, antes de todas as Regras/Cenários
  • Seções Background vazias não produzem saída

Scenario Outline & Examples

Scenario Outlines permitem executar o mesmo cenário com diferentes conjuntos de dados usando placeholders e uma tabela de exemplos.

Sintaxe

Use #### Scenario Outline: em vez de #### Scenario:, depois documente variáveis parametrizadas com <angle_brackets> no texto das etapas. Adicione ##### Examples: com uma tabela pipe fornecendo os dados.

### Requisito: Login
#### Esquema do Cenário: Login com diferentes perfis
- **DADO** usuário <perfil>
- **QUANDO** ele fizer login
- **ENTÃO** ele vê <painel>

##### Exemplos:
| perfil  | painel          |
| admin   | Painel Admin    |
| visualizador | Visão Geral |
| editor  | Editor de Conteúdo |

Gera:

# language: pt
  Regra: Login

    Esquema do Cenário: Login com diferentes perfis
      Dado usuário <perfil>
      Quando ele fizer login
      Então ele vê <painel>

    Exemplos:
      | perfil  | painel          |
      | admin   | Painel Admin    |
      | visualizador | Visão Geral |
      | editor  | Editor de Conteúdo |

Detecção Automática

Se você usar ##### Examples: sob um #### Scenario: comum, ele é automaticamente promovido para Scenario Outline:

#### Cenário: Login (auto-outline)
- **DADO** usuário <perfil>
- **QUANDO** fizer login
- **ENTÃO** <status>

##### Exemplos:
| perfil | status   |
| admin  | sucesso  |
| convidado | negado |

Separadores de Tabela Markdown

Linhas de separação no estilo Markdown (|---|---|) em tabelas de exemplos são ignoradas automaticamente.

DataTables

DataTables no Gherkin fornecem dados estruturados como argumentos de etapas. No OpenSpec, tabelas pipe indentadas sob uma etapa são renderizadas como DataTables.

Sintaxe

- **DADO** que os seguintes usuários existem:
  | nome  | perfil | email            |
  | Alice | admin  | alice@exemplo.com |
  | Bob   | visualizador | bob@exemplo.com |
- **QUANDO** o admin verificar permissões
- **ENTÃO** a lista de usuários está correta

Gera:

# language: pt
    Dado que os seguintes usuários existem:
      | nome  | perfil | email            |
      | Alice | admin  | alice@exemplo.com |
      | Bob   | visualizador | bob@exemplo.com |
    Quando o admin verificar permissões
    Então a lista de usuários está correta

Regras

  • As tabelas pipe devem estar indentadas sob a etapa a que pertencem
  • A primeira linha da pipe se torna o cabeçalho da DataTable
  • As linhas subsequentes se tornam linhas de dados
  • Uma etapa pode ter sub-itens (Doc String) ou uma tabela pipe (DataTable), mas não ambos
  • DataTables funcionam em qualquer idioma Gherkin — o conteúdo da tabela é independente do idioma

Comparação: Doc Strings vs DataTables

FuncionalidadeDoc StringDataTable
SintaxeLinhas - item indentadasLinhas `
Saída Gherkin""" ... """`
Melhor paraTexto livre, saída esperadaDados estruturados chave-valor, múltiplas linhas

Doc Strings

Doc Strings permitem incluir blocos maiores de texto (saída esperada, JSON, XML, etc.) como argumentos de etapas.

Sintaxe

No OpenSpec, sub-itens indentados sob uma etapa são convertidos em Doc Strings Gherkin:

- **ENTÃO** o sistema retorna:
  - status: sucesso
  - token: abc123
  - expira: 3600s

Gera:

    Então o sistema retorna:
      """
      - status: sucesso
      - token: abc123
      - expira: 3600s
      """

Exemplo do Mundo Real

### Requisito: Resposta da API
#### Cenário: Login Bem-sucedido
- **DADO** credenciais válidas
- **QUANDO** o endpoint de login é chamado
- **ENTÃO** a resposta contém:
  - Um token JWT
  - Perfil do usuário com nome e email
  - Timestamp de expiração da sessão
- **E** o código de status é 200

Gera:

# language: pt
  Regra: Resposta da API

    Cenário: Login Bem-sucedido
      Dado credenciais válidas
      Quando o endpoint de login é chamado
      Então a resposta contém:
        """
        - Um token JWT
        - Perfil do usuário com nome e email
        - Timestamp de expiração da sessão
        """
      E o código de status é 200

Delta Specs

Delta specs rastreiam mudanças nos requisitos ao longo do tempo. O OpenSpec suporta três tipos de seção delta: ADICIONADO, MODIFICADO e REMOVIDO.

Seções Delta

Dentro de uma spec de mudança em openspec/changes/<nome-da-mudanca>/specs/, use cabeçalhos H2 para marcar grupos de requisitos:

# Especificação de Autenticação
## Propósito
Requisitos de autenticação atualizados.

## REQUISITOS ADICIONADOS
### Requisito: Login Biométrico
#### Cenário: Autenticar com Impressão Digital
- **DADO** uma impressão digital registrada
- **QUANDO** o usuário escanear sua impressão digital
- **ENTÃO** o acesso é concedido

## REQUISITOS MODIFICADOS
### Requisito: Renovação de Token (Anteriormente: expiração de 1 hora)
#### Cenário: Fluxo de Renovação de Token
- **DADO** um token válido
- **QUANDO** o token estiver prestes a expirar
- **ENTÃO** um novo token é retornado

## REQUISITOS REMOVIDOS
### Requisito: Suporte a Token Legado
Funcionalidade removida — todos os tokens agora usam formato JWT.

Gera:

Funcionalidade: Autenticação

  Requisitos de autenticação atualizados.

  Regra: Login Biométrico

    Cenário: Autenticar com Impressão Digital
      # ADICIONADO
      Dado uma impressão digital registrada
      Quando o usuário escanear sua impressão digital
      Então o acesso é concedido

  Regra: Renovação de Token

    # MODIFICADO: expiração de 1 hora
    Cenário: Fluxo de Renovação de Token
      Dado um token válido
      Quando o token estiver prestes a expirar
      Então um novo token é retornado

  Regra: Suporte a Token Legado
    Funcionalidade removida — todos os tokens agora usam formato JWT.
    # REMOVIDO: Suporte a Token Legado — Funcionalidade removida ...

Localização

O cucumber-openspec suporta todos os 80 idiomas Gherkin. As palavras-chave para Funcionalidade, Regra, Cenário, Dado, Quando, Então, E, Mas, Contexto, Esquema do Cenário e Exemplos são automaticamente traduzidas usando os dados oficiais de idiomas do Gherkin.

Uso

# Português
npx tsx scripts/index.ts -i ./openspec -o ./features -l pt

# Japonês
npx tsx scripts/index.ts -i ./openspec -o ./features -l ja

# Árabe (RTL)
npx tsx scripts/index.ts -i ./openspec -o ./features -l ar

Cabeçalho de Idioma

Para saída em idioma diferente do inglês, o cabeçalho # language: é adicionado automaticamente:

# language: pt
Funcionalidade: Autenticação

  Contexto:
    Dado que o usuário está logado

  Regra: Login
    Esquema do Cenário: Login com diferentes perfis
      Dado usuário <perfil>
      Quando fizer login
      Então <resultado>

    Exemplos:
      | perfil | resultado |
      | admin  | sucesso   |
      | guest  | negado    |
